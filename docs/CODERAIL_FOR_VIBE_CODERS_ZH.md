# CodeRail 是什么：给 Vibe Coder 的项目治理说明

> 让不懂技术的人保留产品决策权，让 AI Agent 承担技术翻译、工程执行和证据说明的责任。

## 一句话定义

CodeRail 是安装在代码仓库里的轻量治理层。

它不替 AI 写代码，也不要求用户先学会编程。它负责让人和 AI 在整个开发过程中持续回答五件事：

1. 我们最终要做成什么？
2. 现在只处理哪一件事？
3. 哪些地方可以改，哪些不能动？
4. 用什么证据证明这件事真的完成了？
5. 换一个会话或换一个 Agent 后，怎样继续而不失忆？

它把答案保存在仓库文档和 Git 历史中，并在任务结束时执行确定性的检查。CodeRail 的核心不是“生成更多文档”，而是让目标、任务、证据和完成状态不再只存在于当前聊天窗口里。

## 为什么 Vibe Coder 需要不同的工作方式

专业程序员和 AI 沟通时，通常能够自己发现不合理的技术建议。他们知道什么时候该追问数据库、权限、并发、测试边界或部署风险。

Vibe Coder 面临的困难不同：

- 不知道有哪些问题尚未被提出；
- 不知道一个技术词代表什么实际后果；
- 难以判断 Agent 是真的完成，还是只完成了表面代码；
- 项目跨越多个会话后，不知道哪些决定仍然有效；
- Agent 很容易优化眼前任务，却逐渐偏离产品目标；
- 当 Agent 给出多个专业方案时，用户可能被迫在自己不理解的选项中“拍板”。

因此，Vibe Coder 最缺的通常不是更多代码生成能力，而是一个可靠的沟通和治理界面。

## 投资人与外包技术团队的类比

可以把 Vibe Coder 看成产品投资人，把 AI Agent 看成外包技术团队。

投资人不需要精通框架、数据库或部署系统，但必须能够决定：

- 产品服务谁；
- 用户最终能做什么；
- 哪些体验不能牺牲；
- 数据和隐私边界是什么；
- 时间、成本和风险如何取舍；
- 哪些结果可以暂时接受，哪些必须停止。

技术团队应当负责：

- 调查代码库已经采用了什么；
- 选择常规、可逆、与现有项目一致的技术方案；
- 实现、测试和验证；
- 把风险翻译成业务后果；
- 只在真正需要产品取舍时请求投资人决定。

一个不好的技术团队会问：

> 你要 PostgreSQL 还是 MongoDB？

一个更好的技术团队会先调查现状，然后问：

> 这批数据是否必须在没有网络时也能使用？我建议先沿用项目现有存储方式，因为本轮只验证单用户流程，而且以后可以迁移。你只需要确认离线使用是不是必须条件。

CodeRail 想建立的正是后一种协作关系。

## CodeRail 解决的四类问题

### 1. 沟通不对称

用户知道产品愿景，但不一定知道技术决策树。Agent 知道大量技术模式，却不一定知道用户真正重视什么。

CodeRail 要求 Agent：

- 能从代码库找到的事实自己调查；
- 把技术问题翻译为用户可观察的结果；
- 给出推荐答案、理由和可逆性；
- 一次只请求一个真正需要用户决定的问题；
- 不把普通实现选择推给非专业用户。

### 2. 目标漂移

长时间开发中，Agent 很容易把“当前文件改成功”误当成“产品正在变好”。

CodeRail 用 `NORTH_STAR.md` 保存总体目标，用当前任务的目标字段把这次修改重新连接到总体目标。Agent 每次开始、检查和收尾时都能看到这条连接。

### 3. 会话失忆

聊天上下文会被清理，模型会更换，电脑也可能更换。只保存在对话里的理解最终都会丢失。

CodeRail 把稳定信息保存在仓库里：

- `NORTH_STAR.md`：总体目标和当前阶段；
- `TASKS.md`：当前任务合同；
- `DECISIONS.md`：重要取舍及原因；
- `HANDOFF.md`：下一会话需要知道的现场状态；
- `PROGRESS.md`：已完成任务及验收证据；
- `TRACELOG.jsonl`：目标、任务、修改和验证之间的追踪关系。

### 4. 虚假完成

Agent 很擅长生成听起来像“已经完成”的总结，但自然语言总结不是证据。

CodeRail 的完成门禁会检查：

- 约定的测试或人工验收是否执行；
- 修改是否超出任务允许范围；
- 禁止修改的文件是否被碰触；
- 验收项是否逐条给出结论；
- 文档、追踪记录和 Git 状态是否一致；
- 提交是否只包含该任务拥有的安全文件。

检查失败时，任务不会被写成完成。

## 实际开发过程中 CodeRail 会做什么

日常界面只有 `start`、`check`、`done` 三个命令。需要切换工作时再使用 `switch`。

### 第一步：开始任务

```bash
python .coderail/coderail.py start "增加课程搜索"
```

Agent 会把一句模糊请求整理成一个任务合同：

| 字段 | 用大白话说 |
|---|---|
| G — Goal | 为什么做，它怎样服务总体目标？ |
| T — Task | 这次只完成哪一件事？ |
| S — Scope | 哪些文件可以改，哪些绝对不能动？ |
| V — Verify | 看到什么证据才算有效？ |
| X — Stop | 出现什么情况必须停下来重新判断？ |
| P — Persist | 哪些结果要写回长期文档？ |

这不是要求用户填写技术表格。正常情况下应由 Agent 调查仓库并起草，用户只确认产品目标、边界和验收结果。

### 第二步：执行与检查

```bash
python .coderail/coderail.py check
```

`check` 回答的不是“代码写了多少行”，而是：

- 当前任务是什么；
- 是否仍然服务 North Star；
- 哪些验收项还缺证据；
- 是否改到了范围之外；
- 当前能不能安全结束；
- 如果不能，下一步具体是什么。

开发过程中的进度汇报应优先使用下面的格式：

```text
现状：用户现在实际能做什么？
问题：哪一个结果还不成立？
证据：测试、日志或界面观察说明了什么？
建议：Agent 推荐怎样处理，为什么？
需要你决定：是否存在真正的产品取舍？
下一步：接下来只做哪一个动作？
```

### 第三步：安全切换

当新问题插入当前工作时，不能假装旧任务已经结束：

```bash
python .coderail/coderail.py switch "修复登录回归"
```

CodeRail 会根据现场状态选择明确路径：

- 当前任务已经验收：先完成并提交，再开始新任务；
- 当前阶段可以验证：提交检查点并暂停；
- 当前改动还不能安全提交：记录现场并要求明确选择；
- 恢复暂停任务：重新取得该任务的文件所有权。

这样可以避免两个任务同时声称拥有同一批未提交修改。

### 第四步：完成任务

```bash
python .coderail/coderail.py done
```

`done` 会：

1. 运行任务约定的验证；
2. 核对每条验收标准；
3. 检查文件范围和敏感文件；
4. 更新任务、进度和追踪记录；
5. 生成精确的安全文件快照；
6. 只提交属于该任务的文件；
7. 给出下一步，或明确说明任务列表已经清空。

自动提交不等于自动推送。发布到远程仍然是独立、可见的动作。

### 第五步：随着项目成长补齐图纸

CodeRail 不要求小项目一开始就画一整套看起来专业、实际可能是猜测的架构图。它会从仓库中的真实信号判断当前是否已经出现前端、后端、数据库、部署、CI、复杂状态或多页面流程，再检查相应图纸是否缺失或已经过期。

Blueprint Gate 覆盖四层、十一类图纸：

- 用户与交互：用户旅程、用户流程、页面流程；
- 系统与应用：系统架构、组件、时序、状态机；
- 数据与模型：ER 图、数据流图；
- 部署与运维：部署拓扑、CI/CD 流程。

```bash
python .coderail/coderail.py blueprint
python .coderail/coderail.py blueprint --scaffold
```

`--scaffold` 只会根据已经检测到的项目结构建立 Mermaid 骨架。Agent 仍须用实际代码中的模块、服务和数据关系替换占位内容，然后才能把图纸标记为 `current`。图纸是对已实现事实的校准和压缩，不是提前虚构未来架构。

### 第六步：登记任务为什么存在、改了什么、由什么证明

CodeRail 把关系分成三个严格隔离的区域：

| 关系 | 谁可以写入 | 例子 |
|---|---|---|
| 可证明事实边 | 本地程序自动登记 | 任务服务哪个 North Star、哪个提交实现任务、提交修改哪些文件、哪项测试验证提交 |
| 重要决策边 | 人或 Agent 显式登记，并给出证据或确认 | `T-046 depends_on T-045`、新任务明确取代旧任务 |
| 候选语义边 | 模型可以提出，但没有执行权限 | “这两个模块可能存在未记录依赖” |

`start`、`switch`、验证和 `done` 会登记能够从任务状态、测试结果和 Git 证明的事实。CodeRail 不会因为某个文件出现在允许范围里，就假装它已经被修改；也不会因为计划运行某个测试，就提前声称测试已经通过。

重要关系使用显式命令登记：

```bash
python .coderail/coderail.py link T-046 depends_on T-045 \
  --reason "使用已经接受的介绍文档合同" \
  --evidence "docs/CODERAIL_FOR_VIBE_CODERS_ZH.md"
```

CodeRail 会检查任务是否存在、是否引用自身、是否形成循环依赖，并在激活任务前检查它依赖的任务是否已经完成。

不确定推断必须先留在候选区：

```bash
python .coderail/coderail.py candidate add T-046 depends_on T-045 \
  --reason "模型怀疑存在未记录依赖"
python .coderail/coderail.py candidate list
```

候选关系不会进入正式图谱，也不能改变任务顺序。只有提供仓库证据或得到明确确认后，`candidate promote` 才会把它晋升为正式决策边。

普通用户不需要阅读图结构，可以直接询问：

```bash
python .coderail/coderail.py why T-046
python .coderail/coderail.py impact docs/BLUEPRINTS.md
python .coderail/coderail.py graph T-046
```

输出会说明这个任务服务什么目标、修改了哪些文件、由哪些测试验证、依赖什么、阻塞什么，以及还有多少未确认候选，而不是输出难以判断的裸节点和边。

## 为什么这样设计

| 常见失败 | CodeRail 的设计回应 |
|---|---|
| Agent 只记得当前对话 | 把稳定状态放进仓库和 Git |
| 一个需求越做越大 | 每个任务声明允许与禁止范围 |
| 用户被迫选择陌生技术 | Agent 调查事实，只请求结果级取舍 |
| 文档写了但没人遵守 | `check` 和 `done` 读取同一份任务合同 |
| Agent 过早宣布完成 | 测试、验收和范围检查共同决定完成 |
| 切换任务后改动归属混乱 | `switch` 管理关闭、暂停、恢复和脏基线 |
| 提交夹带无关文件 | 使用精确安全快照，不执行 `git add .` |
| 失败后状态比之前更乱 | 保留可恢复状态，不把失败伪装成成功 |
| 项目长大后结构只能靠猜 | 根据真实复杂度信号要求补齐并维护最少必要图纸 |
| 任务、文件、提交和验证互相失联 | 自动登记 Git 与生命周期能够证明的事实边 |
| 模型把合理猜测说成事实 | 候选边与正式事实、决策边物理隔离 |
| 规则越来越复杂 | 普通用户仍只需要三个日常命令 |

CodeRail 把需要确定性的部分交给本地程序，把需要判断的部分留给人和 Agent：

- 程序负责状态、范围、验证记录和提交边界；
- Agent 负责调查、解释、建议和实现；
- 用户负责产品结果、风险偏好和不可逆取舍。

## CodeRail 不是什么

CodeRail 不是：

- 更聪明的基础模型；
- 自动生成好产品的保证；
- 专业架构师或产品经理的完整替代品；
- 托管式 CI、工单系统或云服务；
- 要求所有需求先写成完整规格的方法；
- 让 Agent 在没有授权时无限自主运行的调度器。

它也不能消除用户判断。它能做的是把判断题转换成用户有能力回答的形式，并保留做出判断时的证据和上下文。

## 它“科学”吗

目前更准确的说法是：CodeRail 是一个经过工程测试、仍在验证产品假设的方法和工具，不是已经被大规模对照研究证明的通用软件工程理论。

已经有较强证据的部分是：

- 状态转换可以被自动测试；
- 范围冲突可以确定性阻止；
- 任务关闭、失败恢复和精确提交可以做成可重复行为；
- 文档和追踪缺口可以被机器检查。

仍需更多真实项目证据的问题包括：

- 它能在多大程度上减少返工；
- 非专业用户是否更容易做出正确的产品决定；
- 长期项目的目标漂移是否显著下降；
- 额外治理成本在哪种任务规模下才值得。

CodeRail 对 Guided Convergence 的内部 A/B/C 实验也保留了负面结果：面向新手的问题仍然暴露了技术机制，因此结论是 `REVISE`，而不是把实验包装成已经成功。这种“允许证据否定设计”的能力，本身就是 CodeRail 想维护的工作方式。

## 与其他方法的关系

以下比较依据各项目截至 2026-07-27 的官方公开说明。它们解决的问题层级不同，不应简单排名。

| 方法 | 主要解决什么 | 典型流程 | 强项 | CodeRail 与它的关系 |
|---|---|---|---|---|
| GitHub Spec Kit | 把意图逐步变成可执行规格 | Constitution → Specify → Plan → Tasks → Implement | 规格结构、跨产物一致性、组织级约束 | 大型且目标较稳定时可作为上游规格工具 |
| grill-me | 在编码前发现计划中的隐含决策 | 一次一个问题，按依赖遍历决策树 | 主动澄清、问题排序、推荐答案 | 可作为模糊或高风险任务的可选沟通前端 |
| grill-with-docs | 在 grilling 同时沉淀领域语言与重大决策 | Grilling + `CONTEXT.md` + 少量 ADR | 共享语言、跨会话理解 | 可吸收原则，但不建立第二套权威文档 |
| Superpowers | 为 Agent 提供完整工程执行纪律 | Brainstorm → Worktree → Plan → Execute → TDD → Review | 小步实施、TDD、隔离工作区、代码评审 | 可在一个 CodeRail 任务内部作为执行方法 |
| CodeRail | 保持人、Agent、任务、证据和历史持续对齐 | Start → Check/Switch → Done | 仓库内状态、范围所有权、完成门禁、恢复和追踪 | 作为跨方法的治理与持久化层 |

### Spec Kit

[GitHub Spec Kit](https://github.com/github/spec-kit) 官方默认流程强调先定义“做什么”，再形成技术计划、任务并实施。它非常适合目标已经相对清楚、需要多人或多阶段执行的功能。

CodeRail 的出发点不同：Vibe Coder 经常需要通过做原型才逐渐知道自己想要什么。因此 CodeRail 允许先探索，再把已经被证实的内容逐步追认为约束。

两者可以组合：

```text
模糊探索
→ CodeRail 记录已证实的目标和边界
→ 对稳定的大功能使用 Spec Kit 形成 feature spec
→ 每次只激活一个 CodeRail 执行任务
→ CodeRail done 验证并收口
```

组合时必须避免同时维护两套相互冲突的任务真相。可以把 Spec Kit 的 `spec.md` 和 `plan.md` 作为设计输入，但当前执行状态、文件所有权和完成结论应只由一个系统负责。

### grill-me 与 grill-with-docs

Matt Pocock 的 [`grill-me`](https://github.com/mattpocock/skills/blob/main/docs/productivity/grill-me.md) 要求 Agent 沿决策树一次问一个问题，问题附带推荐答案；代码库能回答的事实由 Agent 自己调查。它是用户主动调用、无持久状态的访谈工具。

[`grill-with-docs`](https://github.com/mattpocock/skills/blob/main/docs/engineering/grill-with-docs.md) 在同类访谈中把稳定术语写入 `CONTEXT.md`，把少数难以逆转且真正存在取舍的决定写成 ADR。

CodeRail 与 grilling 不冲突，但对 Vibe Coder 增加一条边界：

> 问用户可观察的结果，不要让用户替 Agent 选择实现机制。

例如不要问“是否使用缓存”，而应问“断网时哪些已经打开的数据必须继续可用”。Agent 再根据代码库和可逆性选择缓存方案。

访谈结果不能只留在聊天里，也不能直接成为未经验证的事实。它应转化为：

- 已确认的目标或产品决定；
- 有证据的代码库事实；
- 明确标注的未知问题；
- 当前任务的验收条件；
- 必要时才进入 `DECISIONS.md` 的长期决定。

### Superpowers

[Superpowers](https://github.com/obra/superpowers) 是 Agent 技能框架和软件开发方法。其官方基本流程包含 brainstorming、独立 Git worktree、细粒度计划、分批或子 Agent 执行、TDD 和代码评审。

它的强项主要位于“专业技术团队怎样高质量执行”。CodeRail 更关注“非专业产品所有者怎样始终知道项目真实状态，并保持决定权”。

推荐的组合边界是：

```text
CodeRail 定义当前任务和验收边界
→ Superpowers 提供 brainstorming、计划、TDD、review 等执行纪律
→ 产出的测试与评审成为 CodeRail 验证证据
→ 只有 CodeRail done 宣布任务完成并提交
```

Superpowers 的技能不应绕过 CodeRail 直接改变任务状态，也不应使用宽泛暂存覆盖 CodeRail 的精确提交边界。

## 四个方法并不相斥

可以把它们理解成三个可选能力层，外面再包一层持续治理：

```text
CodeRail：总体目标、当前任务、范围、证据、恢复和完成门禁
┌─────────────────────────────────────────────────────┐
│ grill-me / grill-with-docs：发现未知，建立共同理解  │
│                    ↓                                │
│ Spec Kit：把稳定意图组织成规格与计划（可选）        │
│                    ↓                                │
│ Superpowers：实施、TDD 和评审等工程纪律（可选）     │
└─────────────────────────────────────────────────────┘
```

这张图不是强制流水线。小任务完全不需要经过全部层级。CodeRail 的原则是按风险增加流程，而不是让每个按钮改名都召开一次需求研讨会。

## 推荐的组合规则

当多个工具同时使用时，先约定权威边界：

1. `NORTH_STAR.md` 是总体产品方向的仓库内入口。
2. CodeRail 当前任务是文件所有权和执行状态的唯一事实来源。
3. Spec Kit 规格可以描述一个大功能，但不要同时让两套 task list 控制当前修改。
4. Grilling 负责发现和澄清，不自动授权实现。
5. Superpowers 技能可以指导实现、TDD 和评审，不直接宣布 CodeRail 任务完成。
6. 只有验证证据可以把“可能正确”变成“已完成”。
7. 自动 hook 只能执行确定性保护，不应调用 LLM 决定用户是否可以继续。

## 最佳工程实践

### 场景一：清楚、局部、容易撤销

例如修改按钮文案或补一个明确的空状态。

```text
CodeRail start
→ Agent 调查现有实现
→ 直接修改并运行小范围验证
→ CodeRail done
```

不要强制 grilling，不要写大型 spec。

### 场景二：目标清楚，但细节有一两个重要未知

例如增加 CSV 导入，但不确定错误数据怎样处理。

```text
Agent 先读代码库
→ 一次询问一个结果级问题并给出推荐
→ 把答案写进 CodeRail 任务验收
→ 小步实现和验证
→ done
```

### 场景三：大型、跨模块、目标已经相对稳定

例如账户、权限和订阅体系。

```text
可选 grilling 建立共同理解
→ 可选 Spec Kit 形成 feature spec 和技术计划
→ 拆成多个可独立验收的 CodeRail 任务
→ 每次只执行一个任务
→ 使用 TDD、review 或 Superpowers 执行技能
→ 每个任务分别 done
```

不要把整个项目塞进一个持续数周的“实现全部功能”任务。

### 场景四：Bug 或回归

```text
先找到能够稳定复现问题的命令或步骤
→ 把失败证据写入 V
→ 再修改代码
→ 运行同一个复现和回归测试
→ done
```

在问题无法复现时，不要用猜测授权大范围重构。

### 场景五：隐私、支付、权限或不可逆数据

```text
先说明用户可见后果和最坏情况
→ 区分事实、假设、决定和未知
→ 请求用户确认业务边界
→ 将高风险未知写入停止条件
→ 采用最小、可逆的实现切片
→ 自动测试 + 必要的人工验收
→ done
```

高风险任务可以增加规格、评审和人工门禁，但仍保持一个权威任务状态。

## Vibe Coder 应该决定什么

| 应由用户决定 | 通常应由 Agent 决定 |
|---|---|
| 服务哪类用户 | 使用项目已经采用的库或模式 |
| 用户必须获得什么结果 | 文件、函数和内部模块怎样组织 |
| 隐私、成本和发布时间边界 | 可逆的技术默认值 |
| 哪种失败是不可接受的 | 测试工具和常规实现细节 |
| 两种产品体验怎样取舍 | 如何修复已复现的普通缺陷 |
| 是否接受不可逆或长期承诺 | 怎样执行格式化、构建和局部重构 |

当技术选择会改变成本、隐私、体验、数据可迁移性或未来承诺时，Agent 应把它翻译成这些后果，再交给用户决定。

## 对 Agent 的沟通要求

用户可以直接要求 Agent 遵守下面的汇报合同：

```text
不要让我从陌生技术名词中盲选。
先调查代码库能够回答的事实。
需要我决定时，请说明：
1. 当前实际情况；
2. 对用户或产品的影响；
3. 你的推荐答案和理由；
4. 决定是否容易撤销；
5. 如果我不决定，任务为什么不能继续。
一次只问一个最重要的问题。
```

这不是要求 Agent 隐瞒技术。用户随时可以要求查看技术细节，但默认界面应先呈现产品后果。

## 怎样判断 CodeRail 是否真的有用

不要以文档数量衡量。更有意义的指标是：

- 完成后又被重新打开的任务是否减少；
- Agent 超出范围的修改是否减少；
- 同一个决定被重复解释的次数是否减少；
- 新会话恢复项目所需时间是否下降；
- 用户被迫回答技术机制问题的次数是否下降；
- `done` 首次通过率是否提高；
- 失败后是否能够恢复，而不留下真假难辨的状态；
- 每个重要修改是否能追溯到目标和验证证据。

如果这些指标没有改善，而流程成本持续增加，就应该简化或停止使用相关机制。

## 最小使用建议

1. 用一页 `NORTH_STAR.md` 写清产品服务谁、提供什么结果、当前阶段是什么。
2. 一个任务只承诺一个可验证结果。
3. 让 Agent 起草任务合同，不让非专业用户填写技术表格。
4. 小任务直接做，高风险或模糊任务才增加 grilling 或规格。
5. 每个进度结论都附带测试、日志或可观察结果。
6. 不同时维护两套当前任务列表。
7. 切换任务时显式暂停或关闭。
8. 永远让 `done` 而不是聊天总结决定任务是否完成。
9. 推送、发布和合并继续作为独立的人类可见动作。
10. 定期回看 North Star；如果反复修复仍不收敛，重新检查设计或目标。

## 最后的定位

CodeRail 不试图证明 Vibe Coder 应该变成专业程序员。

它接受这样一种现实：产品所有者可以不精通实现技术，但仍然能够通过清楚的目标、结果级判断、风险边界和可靠证据，带领一个技术团队做出好产品。

CodeRail 要做的，是让 AI Agent 更像一个负责任的技术团队：

- 自己调查专业事实；
- 用产品所有者听得懂的语言说明情况；
- 不把技术责任转嫁给用户；
- 不忘记长期目标；
- 不越过当前任务边界；
- 不在证据不足时宣布完成；
- 离开前留下下一位 Agent 可以继续的真实现场。

这就是 CodeRail 所说的 **Convergent Coding**：允许探索，但让每一次被证实的理解都成为下一次行动的可靠基础。
